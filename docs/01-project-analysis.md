## 1. رؤية المشروع (Project Vision)

**نظام تسيير موارد بشرية مؤسسي (HRMS) يعمل بالكامل داخل الشبكة المحلية للشركة،** يوفّر إدارة موحدة لدورة حياة الموظف من التوظيف حتى المغادرة، مع تغطية الحضور والإجازات والرواتب والأداء والتدريب، بواجهة عربية/فرنسية/إنجليزية بسيطة، وبنية قابلة للتوسع تدعم أكثر من 5000 موظف في فروع متعددة، **مع بقاء البيانات ملكية كاملة للشركة دون الاعتماد على الإنترنت**.

### بيان الرؤية بصيغة قابلة للقياس

> "بحلول نهاية الإصدار 1.0، يصبح HRMS هو النظام الرسمي الوحيد لتسجيل حضور/انصراف 5000+ موظف، وإصدار الرواتب وقسائمها، ومراجعة الإجازات، دون أي اتصال بالإنترنت، وبدون انقطاع خدمة لأكثر من 99% من ساعات العمل."

## 3. نطاق العمل (Scope)

### 3.1 داخل النطاق (In Scope)

1. إدارة المستخدمين والمصادقة والصلاحيات (RBAC).
2. إدارة بيانات الموظفين الكاملة (بطاقة الموظف، الوثائق، السيرة الوظيفية).
3. الهيكل التنظيمي: الفروع، الأقسام، الوظائف/المناصب، المشرفون.
4. الحضور والانصراف عبر **QR (هاتف/قارئ ثابت)** مع معالجة الاستثناءات (إذن، مأمورية، تعويض).
5. الإجازات: أنواع، رصيد، طلبات، موافقات متعددة المستويات.
6. العقود: أنواع، تواريخ، تجديد، إنهاء.
7. إدارة الوثائق والملفات (تصنيف، صلاحيات، إصدارات).
8. الرواتب: عناصر الأجر، الحضور → كشف راتب، قسيمة، مسارات موافقة.
9. المكافآت والخصومات والعلاوات.
10. التدريب: خطط، دورات، تسجيل، شهادات.
11. تقييم الأداء: أهداف، تقييم ذاتي، تقييم مشرف، مراجعة.
12. الإشعارات داخل النظام + تنبيهات بريد/سطح المكتب داخل LAN.
13. سجل العمليات (Audit Log) الكامل.
14. النسخ الاحتياطي والاستعادة.
15. QR Code لكل موظف (إصدار، إلغاء، إعادة توليد، طباعة).
16. وحدة مساعد ذكاء اصطناعي (تحليلات وتقارير ذكية).
17. التقارير: PDF / Excel / CSV.
18. متعدد اللغات i18n (عربي/فرنسي/إنجليزي).
19. لوحة تحكم (Dashboard) بمؤشرات فورية.

### 5.2 وصف تفصيلي لحالات الاستخدام الحرجة

> **UC-01 — تسجيل الدخول (Authentication)**
>
> - **الممثل:** Guest
> - **الشروط المسبقة:** حساب مفعّل
> - **السيناريو الأساسي:**
>   1. يدخل المستخدم اسم المستخدم وكلمة المرور.
>   2. يتحقق النظام من الاعتماد (hashing + brute-force protection + MFA عند التفعيل).
>   3. يحدد النظام اللغة والعملة والفروع المسموحة من ملف المستخدم.
>   4. يوجه إلى Dashboard حسب الدور.
> - **السيناريو البديل:** 5 محاولات فاشلة → قفل 15 دقيقة؛ انتهاء الصلاحية → إعادة تعيين.
> - **الأمان:** راجع `09-security.md`.

> **UC-04 — طلب إجازة (Leave Request)**
>
> - **الممثل:** Employee
> - **الشروط المسبقة:** رصيد كافٍ، لا إجازة متداخلة، يتبع لفرع نشط.
> - **السيناريو الأساسي:**
>   1. يختار النوع والتواريخ والتعليل.
>   2. يتحقق النظام تلقائيًا من الرصيد والتداخل.
>   3. يمر الطلب لسلسلة موافقات حسب القاعدة `BR-LEAVE-001`.
>   4. عند الموافقة يُخصم الرصيد ويُرسل إشعار.
> - **الاستثناءات:** إجازة مرهونة (Unpaid)، تعارض مع عطلة رسمية (تنبيه لا منع)، فصل مُبرم (Fired) لا يملك طلبات.

> **UC-07 — تسجيل الحضور/الانصراف عبر QR**
>
> - **الممثل:** Employee (هاتف) أو QR Device (قارئ ثابت)
> - **السيناريو الأساسي:**
>   1. يمسح الموظف QR الخاص به.
>   2. يتحقق النظام من: نشاط QR، أن الموظف نشط، الفرع مطابق لفرع الموظف.
>   3. يسجل أول مسح في اليوم كـ `check_in` وثاني كـ `check_out` حسب السياسة.
>   4. يسجل في Audit Log (من، متى، أي جهاز، أي فرع).
> - **الاستثناءات:** QR مكرر/منتهي/ملغى → رفض وتسجيل محاولة تزوير؛ خارج ساعات العمل → تسجيل "خارج الجدول" مع تنبيه؛ مسح من فرع آخر → رفض.
> - **التفاصيل الكاملة:** `06-qr-system.md`.

> **UC-25 — اعتماد كشف الرواتب**
>
> - **الممثل:** HR Manager / Accountant
> - **السيناريو:** المحاسب يولّد الكشف → مراجعة الفروقات → اعتماد HR Manager → تجميد الفترة → إصدار القسائم.
> - **القاعدة الحاسمة:** لا يمكن تعديل بيانات الحضور أو الأجر لفترة مجمّدة إلا بإذن إداري مع تسجيل في Audit Log.

> **UC-27 — المساعد الذكي**
>
> - **الممثل:** HR Manager / أي دور مفوَّض
> - **الوظائف:** أسئلة إدارية، تحليل غياب/أداء/رواتب، تنبؤ بالاستقالات، توليد تقارير باللغة المختارة.
> - **القاعدة:** المساعد **قراءة فقط** على مستوى صلاحيات المستخدم؛ لا يغير بيانات.
> - **التفاصيل:** `07-ai-module.md`.

## 9. سير العمل (Workflows)

> كل Workflow يُوثَّق لاحقًا كـ BPMN في `02-system-design.md`. هنا الوصف الوظيفي.

### WF-1 دورة حياة الموظف (Employee Lifecycle)

```
التعيين → إصدار QR → تفعيل الحساب → العمل (حضور/إجازة/تقييم/تدريب)
         → ترقية/نقل/عقد → إدارة الراتب → نهاية الخدمة (استقالة/فصل/تقاعد)
```

### WF-2 عملية الإجازة

```
طلب → تحقق آلي (رصيد/تداخل/فرع) → [مرفوض نهائيًا | يمر للموافقة]
     → مشرف → (مدير فرع إن لزم) → HR Manager
     → موافقة: خصم الرصيد + إشعار  |  رفض: إشعار + سبب
     → (تعديل الجدول الزمني للفريق من لوحة المشرف)
```

### WF-3 معالجة الحضور اليومي

```
مسح QR → تحقق → تسجيل CheckIn/CheckOut → حساب آلي (تأخير/ساعات/غياب)
       → استثناءات يدوية (إذن/مأمورية/تعويض) بموافقة مشرف
       → تعديلات تصحيح بطلب من الموظف وموافقة مشرف
       → إغلاق الفترة الرواتب → حساب الخصومات
```

### WF-4 الدورة الشهرية للرواتب

```
1) إعداد: مراجعة الحضور والإجازات والعقود → تصحيح الاستثناءات
2) توليد: حساب الأجر (أساسي + عناصر + عمل إضافي + خصومات الحضور)
3) مراجعة: Accountant → مقارنة فروقات → ملاحظات
4) اعتماد: HR Manager → تجميد الفترة
5) إصدار: قسائم PDF → تصدير بنك → أرشفة
```

### WF-5 دورة تقييم الأداء

```
فتح الدورة → توزيع القوالب → تقييم ذاتي → تقييم المشرف → مراجعة نهائية
           → اجتماعات مناقشة → نتائج → PIP للمتعثرين → أرشفة
```

### WF-6 إصدار QR جديد

```
طلب/تعيين موظف → توليد QR (توقيع رقمي) → طباعة البطاقة → تفعيل
      → (إعادة توليد بعد فقدان → إلغاء القديم فورًا) → (إلغاء عند المغادرة)
```

### WF-7 النسخ الاحتياطي اليومي

```
جدولة 02:00 → dump قاعدة البيانات → ضغط + تشفير → تخزين محلي + قرص خارجي/مشاركة LAN
           → تقرير نجاح/فشل إلى IT → اختبار استعادة شهري
```

## 11. تحذيرات وقرارات تصميمية (Alert Box)

> تُقرأ قبل الانتقال إلى المرحلة الثانية.

1. **⚠️ اللغة RTL:** يجب أن يبدأ التصميم بدعم RTL من اليوم الأول (وليس لاحقًا) لأن إعادة هندسة الاتجاهات لاحقًا مكلفة.
2. **⚠️ العملة والتاريخ:** قرر ما إذا كانت الشركة متعددة العملات أم عملة واحدة — يؤثر على نموذج الرواتب.
3. **⚠️ قانون العمل:** قواعد نهاية الخدمة والإجازات تختلف بين الدول — اجعلها **قابلة للتكوين** وليست مبرمجة.
4. **⚠️ الزمن الوظيفي (Effective Dating):** سجلات الموظفين يجب أن تحفظ تاريخ السريان (from/to) للترقيات والرواتب — أساسي للتدقيق.
5. **⚠️ تجميد الرواتب:** لا يُضاف لاحقًا — صممه من البداية، فهو حاجز أساسي للأخطاء المحاسبية.
6. **⚠️ QR مزدوج التقنية:** هواتف + قارئات ثابتة يتطلب واجهة API موحدة للأجهزة — تصميم مبكر.
7. **⚠️ أداء 5000 موظف:** أي تقرير يُبنى على حشو كامل للصفوف سيفشل — خطط للترقيم والتجميع والـ Indexes من البداية (راجع `03`).
8. **⚠️ خصوصية البيانات:** البيانات البنكية والطبية تُعامل كبيانات حساسة مشفرة ومقيدة الوصول.
